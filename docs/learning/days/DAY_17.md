## 4. Concept lesson

### 4.1 The one fact

> **There is no database inside a language model.**

A model is a set of weights — billions of numbers encoding statistical patterns.
When it "tells you a fact", it is not retrieving; it is **regenerating a pattern**
it absorbed during training.

The textbook (1.1) calls this *"the single most important concept for
understanding why RAG exists at all"*, and it is right. Three consequences follow
directly:

**Consequence 1 — it cannot know your documents.** Eternal's Q4 FY26 filing was
not in the training data. Nothing about the architecture allows it to be.

**Consequence 2 — being wrong and being right feel identical.** The mechanism
producing the words is the same either way. There is no internal "I am unsure"
signal unless one was trained in, and even then it is generated by the same
next-token process.

**Consequence 3 — you cannot cite it.** There is no "place" a fact lives. Ask a
bare model for a source and it will generate a plausible one.

**Consequence 3 is the one that decides this system's architecture.** LedgerMind's
product is a traceable answer. A model that cannot cite cannot be the source of
truth; it can only be the *writer*.

---

### 4.2 Tokens

A token is roughly a word-piece: `"revenue"` might be one, `"₹54,364"` several.
Rules of thumb: ~4 characters per token in English; ~750 words per 1,000 tokens.

**Why it matters here, concretely:**

| Where | Consequence |
|---|---|
| **Cost** | Gemini free tier: **500 requests/day**. A semantic query makes **two** calls |
| **Latency** | More tokens in, more time. Measured p50 ~1 s for 200-token calls, ~1.3 s for synthesis |
| **`max_tokens`** | `generate_structured` caps output at 200. Enough for a DSL object; not for prose |
| **Chunking** | `CHARS_PER_TOKEN = 4` in `chunker.py`. Chunk targets are set in tokens and enforced in characters |

`chunker.py` estimates tokens as `len(text) / 4` rather than running a real
tokeniser. Cheap and approximate, and correct for its purpose — the target is a
*budget*, not a hard limit.

---

### 4.3 The context window

The maximum tokens a model can process in one request — prompt **plus** output.

The textbook (1.2) explains the cause: transformer attention compares every token
to every other, so cost grows **quadratically**. Doubling input roughly
quadruples work. The ceiling is arithmetic, not policy.

**The misconception worth killing** (textbook 1.2): *a bigger context window does
not mean you should stuff everything in.*

> Context windows are a ceiling, not a target. Even with a one-million-token
> context window, sending irrelevant information degrades answer quality and
> increases cost.

**LedgerMind's answer**, in numbers: retrieve **top-20**, rerank to **top-5**, and
send five chunks. Not because five is all that fits — because five is what is
*relevant*, and the sixth would dilute rather than help.

You will meet the failure this prevents on Day 30 (textbook 15B, "lost in the
middle").

---

### 4.4 Hallucination, and why "be careful" cannot fix it

A hallucination is fluent, confident, **false** output.

The textbook (1.3) gives the mechanism: the model is a next-token predictor with
no factual grounding, so the process producing a true sentence and a false one is
identical.

**Two pre-RAG approaches, and why both were insufficient:**

| Approach | Why it fails |
|---|---|
| **Fine-tuning on your data** | Expensive, slow to update, and *statistical* — it shifts weights, it does not install verifiable facts. Still no citation, still no access control |
| **Prompt engineering** ("be accurate") | Does not address the root cause: the model still has no access to your data |

**RAG's contribution is structural**, and the textbook states it precisely:

> instead of asking the model to "remember correctly", RAG hands the model the
> actual correct information at the moment it answers … This shifts the problem
> from "can the model remember accurately" (very hard, never fully solvable) to
> "can we retrieve the right document" (a solvable information-retrieval
> engineering problem).

**Read that trade carefully.** RAG does not eliminate the problem — it **moves it
to a place where engineering works**. Retrieval quality is measurable, tunable,
and debuggable. Memory is not.

---

### 4.5 Parametric versus non-parametric memory

| Property | Parametric (weights) | Non-parametric (retrieval) |
|---|---|---|
| Update | retrain | add a document |
| Cost to update | very high | ~zero |
| Auditable | no — cannot trace a fact's origin | **yes — cite the exact page** |
| Private data | requires training on it | native |
| Access control | impossible | metadata filter |
| Hallucination risk | higher | lower, grounded |

**RAG uses both.** Parametric memory supplies language ability and reasoning;
non-parametric memory supplies the facts.

**In LedgerMind, look at how sharply the roles are separated:**

| Task | Which memory |
|---|---|
| Classify a query into a path | parametric (Day 36) |
| Turn a question into a DSL object | parametric (Day 32) |
| Write fluent prose from excerpts | parametric (Day 30) |
| **What Eternal's FY26 revenue was** | **non-parametric — SQL** |
| **What the filing says about risk** | **non-parametric — retrieval** |

**Every fact is non-parametric. Every act of language is parametric.** That line
is the architecture.

---

### 4.6 "LLMs never do math"

`CLAUDE.md` §6, first invariant:

> **LLMs never do math.** DSL → SQL only; derived metrics are Python-side
> arithmetic.

**Why this is structural and not stylistic.** Consider asking a model:
*"Eternal's FY26 revenue was ₹54,364 Cr and FY25 was ₹20,243 Cr. What was the
growth?"*

The model produces a percentage by generating tokens that look like a
plausible answer. It is **frequently right** — which is worse than being
frequently wrong, because it builds trust that the mechanism does not deserve.
And when it is wrong you cannot tell by reading, because the wrong number is
formatted exactly like the right one.

**LedgerMind's answer:** the model emits an eight-field DSL object. Python
computes:

```python
yoy_pct = round((current_val - prior_val) / abs(prior_val) * 100, 2)
```

That line is **verifiable, deterministic and testable**. Nothing about it depends
on a sampling temperature.

**The general principle, worth carrying beyond this codebase:**

> Use the LLM for what only an LLM can do — understanding ambiguous natural
> language. Use deterministic code for everything a computer already does
> reliably.

## 6. Deep walkthrough — what each of the three calls is *for*

### 6.1 Router classification (Day 36)

**Input:** the user's question.
**Output:** `companies[]`, `fiscal_year`, `quarter`, `financial_type`, `path`.
**Why an LLM:** *"Who grew revenue faster, Eternal or Paytm?"* must become
`companies=["ETERNAL","PAYTM"], path="quantitative"`. Regex cannot do this across
arbitrary phrasing.
**What it is not trusted with:** the answer. Only the *routing*.

### 6.2 DSL generation (Day 32)

**Input:** the question plus already-extracted entities.
**Output:** eight fields.
**Why an LLM:** mapping *"top line"*, *"turnover"* and *"revenue from
operations"* onto one canonical metric is a language problem.
**What it is not trusted with:** the SQL, the schema, or any arithmetic.

### 6.3 Semantic synthesis (Day 30)

**Input:** the question plus up to five retrieved chunks.
**Output:** prose.
**Why an LLM:** summarising five passages into a faithful paragraph is exactly
what language models are for.
**What it is not trusted with:** anything not in the chunks. The prompt says so:

```
answer the user's question using ONLY information present in the excerpts.
Do not add outside knowledge. Do not speculate.
```

**Notice the pattern across all three.** The model is asked to *understand* and to
*write*. It is never asked to *know* or to *calculate*.

---

### 6.4 The grounding instruction, read closely

`SYNTHESIS_SYSTEM_PROMPT` opens with the textbook's recommended pattern (15,
"Prompting") — *use only the provided context* — and then adds two things the
textbook does not anticipate, both from measured failures:

```
If the source excerpts refer to the company under a former or different
legal name (for example, following a corporate rename), still treat this
content as directly relevant ... Do not refuse to answer or claim the
documents lack information about the company solely because the name in
the excerpts differs from the name used in the question
```

**Zomato renamed itself Eternal.** A strict grounding instruction made the model
refuse to answer about "Eternal" from documents saying "Zomato" — *correctly
following its instruction*, and uselessly.

```
Reproduce specific proper nouns, legal entity names, and numeric figures
exactly as they appear in the excerpts. Do not paraphrase, abbreviate, or
shorten names (e.g. an auditor's full registered name must be quoted in
full ...)
```

**A model summarising will naturally shorten** "Deloitte Haskins & Sells LLP" to
"Deloitte". For a general assistant that is good style; for an auditable record
it destroys the fact.

**Both additions are the same lesson:** a grounding instruction that is correct in
general can be wrong for your domain, and you only find out by measuring.

## 7. Data flow — where parametric and non-parametric meet

```
                        USER QUESTION
                             │
                    ┌────────▼────────┐
                    │  PARAMETRIC     │  router: understand the question
                    │  (LLM call 1)   │  → companies, period, path
                    └────────┬────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
    ┌───────────────────┐         ┌───────────────────┐
    │  PARAMETRIC       │         │  NON-PARAMETRIC   │
    │  (LLM call 2)     │         │  retrieval        │
    │  question → DSL   │         │  Qdrant → 5 chunks│
    └─────────┬─────────┘         └─────────┬─────────┘
              ▼                             │
    ┌───────────────────┐                   │
    │  NON-PARAMETRIC   │                   │
    │  SQL → Postgres   │                   │
    │  THE NUMBER       │                   │
    └─────────┬─────────┘                   │
              ▼                             ▼
    ┌───────────────────┐         ┌───────────────────┐
    │  DETERMINISTIC    │         │  PARAMETRIC       │
    │  Python arithmetic│         │  (LLM call 3)     │
    │  + a TEMPLATE     │         │  synthesis        │
    └─────────┬─────────┘         └─────────┬─────────┘
              └──────────────┬──────────────┘
                             ▼
                          ANSWER
```

**Read the quantitative branch again.** After the DSL, the LLM is **gone**. SQL
fetches, Python computes, and a **template** — not a generated sentence — writes
the answer. `response_generator.py`:

> quantitative — **TEMPLATED, not generative.** The SQL value is already
> verified; wrapping it in an LLM-generated sentence adds hallucination risk for
> zero benefit.

## 8. Engineering decision — ED-001, "LLMs never do math"

**Problem.** A model asked for a computed figure produces one that is fluent,
unverifiable, and sometimes wrong. Users cannot tell the difference by reading.

**Decision.** The LLM emits a DSL object. A deterministic Python compiler
produces parameterised SQL. All arithmetic is Python over values fetched from
Postgres. The model never writes SQL and never sees the schema.

| Alternative | Why not |
|---|---|
| **Text-to-SQL** | The model would need the schema, and generated SQL can be syntactically perfect and semantically wrong. There is no validator for "this SQL answers a different question" |
| **Let the model compute from retrieved tables** | Transcription plus arithmetic, both unverifiable. This is what the naive design does |
| **Model computes, code verifies** | You would need the correct answer to verify against — at which point compute it and skip the model |
| **Function calling / tools** | Closer, and still lets the model choose arguments freely. The DSL is a **narrower** tool: eight fields, each validated (Day 32) |

**Trade-offs accepted.**

- **Coverage.** Only questions expressible in eight fields and five operations
  can be answered quantitatively. Anything else refuses (Day 34) — and
  `CAVEAT-004` records that the schema cannot express "no metric".
- **A compiler to maintain.** `dsl_compiler.py` is 303 lines that a text-to-SQL
  prompt would not need.
- **Two LLM calls** on a semantic query, against a 500/day ceiling.

**Current validity.** Central. Everything measurable about this system rests on
it: `sql_verified` means something only because a deterministic path produced the
number.

**At 10×.** Unchanged. If anything the argument strengthens — more users means
more wrong answers per unit of hallucination.

## 9. Failure modes

| Symptom | Cause |
|---|---|
| A fluent, wrong number | The model computed it. Should be impossible here — check whether a template or a generated sentence produced it |
| A plausible citation to nothing | The model invented a source. Prevented by citations being built from retrieval, not generated |
| A refusal about a renamed company | Grounding instruction too strict — the Zomato/Eternal case |
| A shortened entity name | The model summarised. Countered by the "reproduce exactly" instruction |
| Quota exhausted mid-sweep | 500/day, two calls per semantic question |
| Answer ignores provided context | Faithfulness failure; grounding instruction too weak (textbook 15B) |
| Truncated structured output | `max_tokens=200` on `generate_structured` |

## 13. Answer key

> **Only read after attempting.**

### §11

1. **The fact:** there is no database inside the model; it regenerates patterns.
   **Consequences:** (a) it cannot know your private or recent documents;
   (b) being right and being wrong feel identical, because the same mechanism
   produces both; (c) it cannot cite, because no fact has a location.
   **(c) decides the architecture** — LedgerMind's product is a *traceable*
   answer, so the model cannot be the source of truth. It can only be the writer.
2. **quantitative** — templated, no LLM, because "the SQL value is already
   verified; wrapping it in an LLM-generated sentence adds hallucination risk for
   zero benefit". **semantic** — generative, because "there's no ground truth
   number to protect — only retrieved text to summarise faithfully".
   **cross** — generative plus a contradiction disclosure block.
3. **Router classification** — trusted to *understand* the question and pick a
   path; not trusted with the answer. **DSL generation** — trusted to map prose
   onto a canonical metric and operation; not trusted with SQL, the schema, or
   arithmetic. **Semantic synthesis** — trusted to *write* from supplied
   excerpts; not trusted with anything not in them.
4. Generated SQL can be **syntactically perfect and semantically wrong**, and
   there is no validator for "this query answers a different question than the
   one asked". Validation catches injection and malformed syntax; it cannot catch
   a correct query against the wrong metric or period. The DSL is validated
   against a *closed vocabulary* — eight fields, a registry of metrics, five
   operations — so "invalid" is decidable. With free-form SQL it is not. (Second
   argument: the model would need the schema, widening what a prompt injection
   could reach.)
5. Because the target is a **budget, not a hard limit**. `len(text) / 4` is
   accurate enough to keep chunks in the right size band, and running a real
   tokeniser over every candidate split during recursive chunking would cost far
   more than the precision is worth. Chunk boundaries are chosen by separator
   anyway, so an exact count would not change where the split lands.

### §12 — Basic

1. Weights — billions of numbers encoding statistical patterns from training. No
   database, no lookup table, no stored documents.
2. Roughly a word-piece; about four characters of English.
3. The maximum tokens (prompt + output) in one request. The limit exists because
   transformer attention compares every token to every other, so cost grows
   quadratically with length.
4. **Parametric:** knowledge baked into weights — static, unauditable, updated
   only by retraining. **Non-parametric:** knowledge stored externally and
   fetched at query time — instantly updatable, auditable, access-controllable.
5. **Three**: router classification, DSL generation, semantic synthesis. All go
   through `app/llm/client.py`.

### §12 — Code

6. Classify a query into a path; convert a question into a DSL object; write
   prose from retrieved excerpts.
7. **Quantitative.** The value is already SQL-verified, so generation would add
   hallucination risk for no benefit.
8. `max_tokens=200`. Enough for an eight-field JSON object; deliberately too
   small for prose, which is a second guard against the structured call drifting
   into generation.
9. `chunker.py`, as `CHARS_PER_TOKEN = 4`. It converts token-denominated chunk
   targets into character counts.
10. Outside knowledge and speculation — *"answer using ONLY information present
    in the excerpts"*. It also forbids paraphrasing proper nouns and figures, and
    forbids repeating citation details in prose (the system appends those
    separately).

### §12 — Why

11. Because no fact has a location in the weights. A "source" would have to be
    generated like any other token — which is why bare models invent plausible
    citations.
12. Because it does not address the root cause. The model still has no access to
    your data, and the mechanism generating a false sentence is identical to the
    one generating a true one. You are asking it to be careful about something it
    cannot check.
13. (a) **Cost and staleness** — expensive, and slow to update for data that
    changes quarterly. (b) **No attribution** — you cannot cite which document a
    fine-tuned fact came from. (c) **No access control** — you cannot fine-tune a
    model to show different users different documents; RAG does that natively
    with a metadata filter.
14. Because the number is already verified by SQL, and a generated sentence could
    transcribe it wrongly while looking identical. The template cannot.
15. Because irrelevant context **degrades** answer quality and costs money and
    latency. The window is a ceiling. LedgerMind sends five chunks because five
    are relevant, not because five is the maximum.

### §12 — Debugging

16. The grounding instruction was too strict: told to use only the excerpts, the
    model correctly concluded that documents about "Zomato" do not discuss
    "Eternal". Fixed by the rename clause in `SYNTHESIS_SYSTEM_PROMPT`, which
    tells it to check whether the excerpts describe the same corporate entity
    before concluding they are unrelated.
17. The "reproduce specific proper nouns, legal entity names, and numeric figures
    exactly as they appear" clause, with the auditor's full registered name given
    as the worked example. Summarisation naturally shortens names; for an
    auditable record that destroys the fact.
18. A **quota** signature. `CLAUDE.md` §5: failure at a *fixed position* with
    everything before it passing is quota exhaustion. A real defect fails by
    **category**, scattered through the run.

### §12 — System design

19. **Refuse.** ED-001's argument applies unchanged: a computed figure from the
    model is fluent, unverifiable, and sometimes wrong, and the user cannot tell
    by reading. Refusing costs the user two minutes; a confident wrong figure can
    cost them a decision, and it spends the system's credibility to do it. This
    is exactly what `quant_engine`'s Stage 0 guard does for derived metrics — it
    refuses **before any LLM call**, explains that the metric is derived and the
    compiler does not yet support it, and suggests querying the components
    (Day 34). The right long-term answer is to extend the compiler, not the
    model's licence.
20. **What it buys:** retrieval quality is *measurable, tunable and debuggable*.
    You can inspect what was retrieved, score it, set thresholds, and write a
    golden dataset that asserts exact values. None of that is possible against
    "did the model remember correctly". It also buys instant updates, citation,
    and access control. **What it costs:** an entire retrieval system to build and
    maintain — chunking, embedding, a vector store, fusion, reranking,
    confidence calibration — plus a new failure surface where the *retrieval*
    is wrong rather than the model. Days 20–29 are that cost, itemised.

```text
  (unsolvable) to retrieval (an engineering problem)
- Why fine-tuning fails on three independent grounds, not one
- Why a validated generated SQL query is still not safe: validity is decidable,
  "answers the right question" is not
- Why a grounding instruction correct in general can be wrong for your domain,
  and that you only find out by measuring
```
